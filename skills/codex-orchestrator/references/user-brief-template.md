# Human-Readable Review Brief Template (Gemini Manager -> User)

Use this structure whenever presenting Codex `implement`, `consult`, or `review` results to the user. **Never paste Codex's raw text or JSON directly.**

```markdown
### 一、结论（TL;DR）
<!-- 1–2 句自然中文直说结果：问题是否已解决 / 根因是什么 / 改动是否通过独立验收、能否直接合入或等待拍板。 -->

### 二、为什么这么改 / 核心脉络
<!-- 用业务与逻辑语言讲清“原问题 -> 解决思路 -> 实际变化”。
     先写人话概念，括号内附具体文件名或符号名；涉及多步流程、架构对比或方案权衡时，配 Before/After 对比表或精简 Mermaid 流程图。 -->

### 三、关键变更地图
| 文件 | 改动职责 | 影响范围 |
| :--- | :--- | :--- |
| [basename](file:///abs/path) | <用人话说明这段改动负责什么> | <影响哪些模块或无副作用> |

### 四、独立验收与事实抽查
- **Codex 执行情况**：<简述各路 Codex 完成情况、模型/思考强度/速度档与产物路径；如走 DAG 并行，说明工作流阶段与 `merge_ok` 状态>
- **Worker 与本地/远端检查**：<列明由 `codex-worker` 已执行并通过的单元测试、补丁检查或跨机 SSH 同步/实测，避免重复重跑>
- **Gemini 独立复核（分层门禁）**：
  - **Diff 与范围检查**：<确认仅改动允许范围内文件，跨路补丁无重叠或已妥善合流，无遗留调试产物>
  - **关键事实抽查**：已直接核实 `<1–2 处核心改动或 review 引用的 file:line>`（严格区分“已核实事实”与“未运行/待验证推测”）
  - **高层门禁验证**（如多卡 GPU smoke、断点续训或端到端检查）：`<实际执行的验证命令>` -> <观察到的真实通过/失败结果>

### 五、风险与待拍板事项
- <如有取舍、未覆盖场景或阻塞项，给出 1–3 个清晰选项请用户拍板；若无，明确写“当前无阻塞风险”。>
```

## 表达红线
1. 严禁直接复制粘贴、翻译腔照搬 Codex 的 `last_message.md`。
2. 不要按时间流水账汇报（禁止“先读了 A、再 grep 了 B、然后改了 C”）。
3. 禁止把一串未解释的代码符号/变量名当句子主语。
4. 仅陈述实际核验过的文件、改动、命令与结果；未实跑或未抽查的事项必须明确标出。
